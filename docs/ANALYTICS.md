# Analytics definition

API periods are 1, 7, or 30 days ending at request time. Boundaries are inclusive; calculations and chart labels use UTC. PostgreSQL should run in UTC (configured in Compose). Browser dates shown on the dashboard use UTC as well.

Uptime percentage is `successful observed checks / total observed UP or DOWN checks × 100`. No observations returns `null`, rendered as an em dash. This is sample availability, not a continuous-time SLA. A failed observation counts against observed uptime even if a failure threshold has not yet opened an incident. Paused monitors retain prior history but do not generate checks while paused. Missed scheduler intervals, outages of the worker, and unsampled periods are unknown; they are never fabricated as success or downtime. Daily bars aggregate actual observations, show partial uptime in amber, complete failure in red, and missing history in gray, with labels and tooltips.

Response statistics include all completed observations with a measured latency, including failures. Latency includes DNS and the time until response headers; bodies are not downloaded. Average, minimum, maximum, and latest latency are provided. Chart buckets are 15 minutes for 24 hours, 1 hour for 7 days, and 6 hours for 30 days. Chart averages are computed by PostgreSQL over indexed check timestamps. Dashboard averages are weighted by observed check counts. A bucket without an observation is absent from the result; the chart has no synthetic zero samples.

Downtime sums the overlap of confirmed incident intervals with the reporting window. It starts when the configured consecutive-failure threshold is reached. Open incidents run to request time. Configuration resets and pause/resume terminate an open incident without claiming an HTTP recovery; their detail view explains that an end can result from a configuration change. Total incidents counts incidents overlapping the period. Charts and incident-duration measurements answer different questions and can differ intentionally.

Check retention defaults to 90 days and is configurable with RETENTION_DAYS (minimum 30). An hourly worker maintenance task deletes older checks and expired sessions/reset tokens. Incidents and delivery history remain until their owning monitor is deleted. Cascading monitor deletion is immediate and irreversible; the UI asks for confirmation. Indexes support monitor/time history, due-job claims, and outbox claims. At larger scale add daily rollups, partition check storage, and batch retention deletes.

Development seed history is explicitly labeled demo data and persists in the same schema as real checks. The seed never touches an existing demo workspace; subsequent worker observations replace no history. New registrations have no seeded observations.
